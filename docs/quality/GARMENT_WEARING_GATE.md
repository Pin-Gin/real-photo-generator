# 衣装変更 — 必須QAゲート（T-020E以降）

**記録日:** 2026-11-28  
**適用:** `Pin-Gin/real-photo-generator` の衣装生成検証すべて。会話で確定したユーザー要求を明文化したもの。旧FIXED要件本文の改訂ではない。

## 合格の定義（両方必須）

**G1｜人物Masterの身体全体の一貫性**

- 顔の類似だけでなく、首の長さ・付け根、肩幅、鎖骨、胸郭、胴体、腰・骨盤、腕・脚・手足の接続、頭身・体格を評価。
- 身体形状をマネキンの寸法・透明材質で置換しない。ポーズ参照を使う場合も、マネキンから取得するのは**姿勢情報のみ**。
- 首が不自然に伸びる、胸郭・肩・四肢の接続が破綻する場合、衣装がきれいでも**総合FAIL**。

**G2｜服を『着せている』こと**

- 参照衣装の着用に必要な立体構造（身頃、袖、襟、開口部、スカート、接続／縫い目、装飾の取り付き）と、体との接触・布の厚み・張り・たるみ・重力方向・自然な層の前後関係が成立すること。
- 旧衣装を透明化して新衣装を上から被せる、ガラス状マネキンの身体を転写する、リボンやフリルだけを追加する、衣服の画像を平面的に貼る表現は**総合FAIL**。
- **透ける素材そのものは不合格理由にしない。** NGなのは透けを利用した旧衣装・透明身体との不整合や衣服の物理的な着用破綻。参照衣装の意匠と透明度を勝手に不透明・別意匠へ変更しない。
- 衣装の色・装飾・全身構造が参照に適合していても、G1またはG2がFAILなら総合PASSにしない。

## 入力役割と変更禁止

- **人物Master:** 顔・髪・体格・全身の身体比率・人物性の参照。顔だけの切り抜きによる代替を**採用しない**。
- **衣装画像:** 布の色・素材・透け具合・形・装飾・構造の参照。透明マネキンの体格・透明身体・背景を参照しない。
- **ポーズ:** Masterの比率を変えずに姿勢だけ適用する。現段階はポーズ変更を混ぜず衣装制御を先に試験。
- **生成方式:** ユーザーの指示に従い**元Masterの画像を編集・上書きする衣装合成方式を使用しない**。新規生成は新しい潜在画像から行う。ただし、`EmptyLatentImage`を使ったという形式だけでG1/G2達成とはしない。
- 画像入力の役割を指定してもモデルが完全に分離解釈する保証はない。画像の参照役割を切り分けられる設計とQAが必要。
- 成功原本、seed、モデル等の設定は保全。失敗版を成功ワークフローへ昇格しない。比較時は実際に変更した変数を明記する。

## T-020E｜今後の検証ゲート

1. **E-01 技術棚卸し:** ComfyUI `/models/loras`、`/models/controlnet`、`/models/diffusion_models`、`/object_info` から、衣装転写用LoRA／身体構造制御ノード・モデルの導入状況を読み取り専用で確認。インストール済みと文献上の存在を混同しない。
2. **E-02 方式選定:** 「新規潜在からの生成」「全身身体構造のガイド」「衣装だけの参照・必要なら透明マネキンからの衣装抽出」が**一緒に成立するワークフロー**だけを採用候補にする。通常のVirtual Try-Onは人物元画像を編集する方式があるため、**ユーザーの新規生成要件との適合を先に確認**。
3. **E-03 単独試験:** まず自然な身体を保ち、衣服を実際に着用した新規画像を生成できるか確認。その後、ラベンダー色の参照衣装で構造と着用の再現性を測る。衣装を不透明化してSFW要件を満たしたように見せない。複数条件を同時に無秩序に変えない。
4. **E-04 結果QA:** G1、G2、衣装意匠、人物同一性、ポーズ・構図・背景を**個別**にPASS/WARN/FAIL。**G1/G2はハードゲート**。最終判定はユーザー画像評価に従い、結果・失敗理由・次の変数を台帳へ記録。

## T-020E 生成前の構造検査（2026-11-28追加）

- **実装:** [`scripts/validate_t020e_workflow.py`](../../scripts/validate_t020e_workflow.py)（Python標準ライブラリのみ）。ComfyUI API形式のJSONと2つのLoadImageファイル名を受け取り、違反時は`REJECT`／終了コード2。条件合格でも`STRUCTURAL_PRECHECK_PASS (NOT IMAGE QA PASS)`と表示する。
- **事前に拒否するもの:** 人物Masterの同一性参照経路の欠落、衣装画像参照の欠落、Master由来のOpenPose→ControlNet構造経路の欠落、空の潜在ではない編集方式、アダプター重み0、ControlNet強度0。**E-03Aの「ポーズだけMaster、衣装は文章だけ」構成は拒否対象**。
- **試験:** [`tests/unit/test_validate_t020e_workflow.py`](../../tests/unit/test_validate_t020e_workflow.py) の8テスト。開発環境では`python -m unittest discover -s tests/unit -p 'test_validate_t020e_workflow.py' -v`で検証。今回のコンテナ内で同等の8ケース合格を確認済みだが、ユーザーPC・ComfyUI実機での実行は未確認。
- **適用規則:** 以降、T-020Eの新規API JSON生成案は、提案前に構造検査とテストの結果を照合。構造FAILならユーザーに生成を依頼しない。既存の成功設定を無断変更しない。
- **適用範囲の限界:** このチェックは**参照画像が条件付けに接続されていること**を検証するだけ。Masterの全身比率が本当に保持されるか、衣装が本当に着用されるか、透明マネキンが転写されないか、モデル重みがComfyUIで正しくロードできるかは判定できない。G1/G2の最終承認は実画像QAが必要。誤って「PASS＝衣装問題解決」と扱わない。
- **現在の運用上の限界:** 過去に渡した任意PowerShellから`/prompt`へ直接POSTすれば検査を迂回できる。**現時点でAPI呼び出し自体が自動的にブロックされるわけではない**。今後提示する生成手順に検査の実行を必須として組み込み、検査を通らないものは送信しない。
